# 代码的坏味道 — 24 种判据与处方

来源：《重构：改善既有代码的设计》第 2 版，第 3 章（Kent Beck & Martin Fowler）。
每条含：识别特征 → 处方（书中手法名）→ 本仓库映射（如适用）。
手法后的编号指 `catalog.md` 中的章节号。

书的总纲："没有任何量度规矩比得上见识广博者的直觉"——坏味道是**迹象**，不是罪证；
每条发现仍须过 SKILL.md 的五道裁决（行为可验证/经济值得/可小步/帽子分清/YAGNI）。

---

## 1. 神秘命名（Mysterious Name）

- **识别**：函数/变量/类的名字无法说明自己的功能和用法；读者需要"猜谜"。想不出好名字本身往往暗示更深的设计问题。
- **处方**：改变函数声明（6.5）、变量改名（6.7）、字段改名（9.2）。
- **本仓库**：代码标识符英文、文案中文——名字里混入拼音或中式缩写即中此味。engine 导出名应说明"做什么"（`clubTrophyCandidates`）而非"怎么做"。

## 2. 重复代码（Duplicated Code）

- **识别**：一处以上出现相同代码结构；读者被迫比对细微差异；改一处必须找出所有副本。
- **处方**：提炼函数（6.1）；相似而不相同 → 先移动语句（8.6）归拢再提炼；同超类的子类间重复 → 函数上移（12.1）。
- **本仓库**：事件 resolve 里重复的赔率/文案构造是高发区——先看 `pct()`/`clampOdds` 等既有 helper 是否已覆盖；UI 的标签重复应收进 `ui/vocabulary.ts`。

## 3. 过长函数（Long Function）

- **识别**：判据不是行数，而是"做什么"与"如何做"的语义距离。需要注释来说明的代码段、条件表达式、循环，都是提炼信号。
- **处方**：提炼函数（6.1）为主；临时变量碍事 → 以查询取代临时变量（7.4）；参数太多 → 引入参数对象（6.8）+ 保持对象完整（11.4）；杀手锏 → 以命令取代函数（11.9）；条件 → 分解条件表达式（10.1）；大 switch → 每分支提炼函数；循环 → 提炼 + 拆分循环（8.7）。
- **本仓库**：`buildPeriodDecisions`、`simOneSeason` 这类编排函数允许长（编排本身就是"做什么"），但其中每个内嵌决策块应可命名；App.tsx 内联组件超过一屏且承担多个 UI 职责时适用。

## 4. 过长参数列表（Long Parameter List）

- **识别**：参数彼此可推导、总是成组出现、或含控制行为的 flag。
- **处方**：以查询取代参数（11.5）、保持对象完整（11.4）、引入参数对象（6.8）、移除标记参数（11.3）、函数组合成类（6.9）。
- **本仓库**：`EventContext` 就是"引入参数对象"的既成范例——新的事件相关函数应收参 `ctx` 而非再铺散参数。

## 5. 全局数据（Global Data）

- **识别**：代码库任何角落都可修改、且无法追踪谁改了它的数据（全局变量、类变量、单例）。剂量决定毒性。
- **处方**：封装变量（6.6），再把函数与数据搬进模块收窄作用域。
- **本仓库**：engine 必须零副作用——localStorage 只准出现在 `meta/legacy.ts`；模块级可变状态需要 `setPreviewsEnabled` 级别的书面理由。

## 6. 可变数据（Mutable Data）

- **识别**：一处更新、别处期望旧值；派生值被手工维护而非计算。作用域越大风险越高。
- **处方**：封装变量（6.6）、拆分变量（9.1）、移动语句（8.6）+ 提炼函数（6.1）分离无副作用逻辑、将查询函数和修改函数分离（11.1）、移除设值函数（11.7）、以查询取代派生变量（9.3）、函数组合成类/变换（6.9/6.10）、将引用对象改为值对象（9.4）。
- **本仓库**：`RngState` 原地 mutation 是豁免项（性能决策）；但 `Modifiers` 合并、`pendingMods` 累积之外的原地改 `GameState` 都算此味——mutation 应集中在 engine 编排层。

## 7. 发散式变化（Divergent Change）

- **识别**：一个模块因**不同原因**在不同方向反复被改（"加数据库要改这 3 个函数，加金融工具要改那 4 个"）。上下文没有分开。
- **处方**：拆分阶段（6.11）（变化方向有先后次序时）、搬移函数（8.1）建模块分开、先提炼函数（6.1）再搬、类形式 → 提炼类（7.5）。
- **本仓库**：若某文件同时因"赔率调平衡"和"文案改写"被反复触碰，就是把 odds 与 copy 混在一处的信号（近期把 odds 折叠进事件目录正是此味的解法）。

## 8. 霰弹式修改（Shotgun Surgery）

- **识别**：与发散式变化相反——**一种**变化要在许多不同地方各改一点；容易漏改。
- **处方**：搬移函数（8.1）/搬移字段（8.2）收拢、函数组合成类（6.9）、函数组合成变换（6.10）、拆分阶段（6.11）；常用策略：先内联函数（6.2）/内联类（7.6）把散逻辑拽回一处，再重新提炼。
- **本仓库**：高发场景是"新增一个 Trophy/事件/祝福要同步改 N 个 `Record` 映射"。TS 的穷尽检查会把漏改变成编译错，但收拢进 `vocabulary.ts` 一处仍是正解。

## 9. 依恋情结（Feature Envy）

- **识别**：一个函数与**别的**模块的数据/函数交流远多于自己所在模块。
- **处方**：搬移函数（8.1）；只有一部分依恋 → 先提炼函数（6.1）再搬。原则：**把总是一起变化的东西放在一块儿**；数据和引用它的行为通常一起变化。
- **本仓库**：App.tsx 里出现纯计算（不碰 JSX）而反复读 engine 数据的函数，应搬去 engine 或 `ui/vocabulary.ts`（tier-color 迁移即先例）。

## 10. 数据泥团（Data Clumps）

- **识别**：相同的三四项数据总是成群出现（多个签名里的相同参数、多个类的相同字段）。测试法：删掉其中一项，其余是否失去意义？
- **处方**：提炼类（7.5）、引入参数对象（6.8）、保持对象完整（11.4）。得到新类后顺藤摸瓜找依恋情结，把行为也搬进去。

## 11. 基本类型偏执（Primitive Obsession）

- **识别**：用裸 number/string 表达领域概念（钱、范围、电话号码）；"stringly typed"。
- **处方**：以对象取代基本类型（7.3）；类型码 → 以子类取代类型码（12.6）+ 以多态取代条件表达式（10.4）；成组基本类型 → 见数据泥团。
- **本仓库**：`"name@ttl"` 标签编码是豁免项——但**绕开** `ttlTag`/`decayTag`/`dedupeTags` 裸拼/裸 split 字符串即中此味；新领域概念（如赔率、年龄段）先找 `types.ts` 里是否已有类型别名。

## 12. 重复的 switch（Repeated Switches）

- **识别**：同样的条件分支逻辑（switch 或 if/else 链）散布多处——新增一个分支要找齐所有 switch 逐一更新。
- **处方**：以多态取代条件表达式（10.4）。
- **本仓库**：TS 惯用解是判别联合 + 穷尽 `Record`/switch（编译器兜底），或收进 `vocabulary.ts` 单点映射；同一 tier 阈值链在两处出现即中此味（`ovrTierClass`/`oddsClass` 是收口先例）。

## 13. 循环语句（Loops）

- **识别**：命令式循环掩盖了"筛选/映射/汇总"的意图。
- **处方**：以管道取代循环（8.8）（filter/map 让被处理元素与处理动作一目了然）。
- **本仓库**：低优先级——engine 热路径上的 for 循环若有实测性能理由可保留，注明即可。

## 14. 冗赘的元素（Lazy Element）

- **识别**：不再赚回自身结构成本的程序元素——名字与实现一模一样的函数、只剩一个函数的类、"将来会变大"却从未变大的抽象。
- **处方**：内联函数（6.2）、内联类（7.6）、继承体系中 → 折叠继承体系（12.9）。

## 15. 夸夸其谈通用性（Speculative Generality）

- **识别**："总有一天会用到"的钩子、特殊情况处理、只有测试用例在使用的函数/类。
- **处方**：折叠继承体系（12.9）、内联函数/类（6.2/7.6）、改变函数声明（6.5）去掉未用参数、移除死代码（8.9）。
- **本仓库**：`noUnusedLocals` 会抓死导出，但"被 tools/ 某个一次性脚本引用着的 engine 导出"是盲区——只有法证脚本在用的引擎 API 应质疑。

## 16. 临时字段（Temporary Field）

- **识别**：某字段只为特定情况而设，其余时间为空——读者被迫猜测它何时有意义。
- **处方**：提炼类（7.5）给孤儿安家、搬移函数（8.1）跟进、引入特例（10.5）消除"不合法时"的条件检查。
- **本仓库**：`GameState` 上 optional 字段增殖是此味的早期信号——问一句"它是否只在某个 phase 有意义"，是则考虑收进该 phase 的专属结构。

## 17. 过长的消息链（Message Chains）

- **识别**：`a.b().c().d()`——客户端与导航结构紧耦合，中间任何关系变化都殃及客户端。
- **处方**：隐藏委托关系（7.7）；更好的选择：看链尾对象被用来做什么，提炼函数（6.1）+ 搬移函数（8.1）把使用代码推入链中。
- **注意**：书中明确"并非所有函数链都是坏东西"——短链、只读、稳定结构的链不必动。

## 18. 中间人（Middle Man）

- **识别**：某类接口一半以上的函数都只是委托给另一个类。
- **处方**：移除中间人（7.8）、少量委托函数 → 内联函数（6.2）；中间人还有行为 → 以委托取代超类/子类（12.11/12.10）。

## 19. 内幕交易（Insider Trading）

- **识别**：两个模块私下大量交换数据；子类对超类内部了解过多。
- **处方**：搬移函数（8.1）/搬移字段（8.2）减少私聊、共同兴趣 → 新建模块或隐藏委托关系（7.7）、继承密谋 → 以委托取代子类/超类（12.10/12.11）。
- **本仓库**：`events.ts` import `ttlTag` from `run.ts` 是唯一豁免的跨边；新增任何 engine 内跨模块 import 前先问"该逻辑属于谁"。

## 20. 过大的类（Large Class）

- **识别**：字段太多（随之而来必是重复代码）；或使用者只用到功能的某个子集——每个子集都是拆分线索。相同前缀/后缀的字段组是提炼信号。
- **处方**：提炼类（7.5）、提炼超类（12.8）、以子类取代类型码（12.6）；类内代码重复 → 先把大函数拆小再消重。
- **本仓库**：App.tsx 整体豁免（文档化决策），但其中**单个**内联组件失控时适用；engine 侧 `run.ts` 若编排之外长出第二职责（如文案生成），按发散式变化处理。

## 21. 异曲同工的类（Alternative Classes with Different Interfaces）

- **识别**：两个类做类似的事，接口却不一致——失去互相替换的可能。
- **处方**：改变函数声明（6.5）统一签名、搬移函数（8.1）对齐协议、产生重复 → 提炼超类（12.8）。

## 22. 纯数据类（Data Class）

- **识别**：只有字段和取值/设值函数的"不会说话的数据容器"，被其他类过分细琐地操控——行为放错了地方。
- **处方**：封装记录（7.1）、移除设值函数（11.7）、把调用端行为用搬移函数（8.1）搬进来。
- **例外（书中明示）**：作为函数返回结果的不可变中转数据结构（拆分阶段（6.11）的产物）无须封装——本仓库 engine 的 `ResolveResult`、`FiredEvent` 等纯数据结构正属此列，**不算**坏味道。

## 23. 被拒绝的遗赠（Refused Bequest）

- **识别**：子类只挑超类礼物中的几样来玩。气味通常不浓——只复用实现而不用全部接口，十有八九不值得理睬；**拒绝支持超类接口**才是浓烈信号。
- **处方**：函数下移（12.4）/字段下移（12.5）给兄弟类；拒绝接口 → 以委托取代子类（12.10）/以委托取代超类（12.11）。
- **本仓库**：engine 无继承体系，此味主要防"为复用而引入继承"的新增代码——TS 里优先组合与判别联合。

## 24. 注释（Comments）

- **识别**：注释本身是香味；坏味道是把它当"除臭剂"——长注释往往在补偿糟糕的代码。
- **处方**：需要注释解释"做了什么" → 提炼函数（6.1）；函数已提炼仍需解释 → 改变函数声明（6.5）改名；需要说明需求规格 → 引入断言（10.6）。**当你感觉需要写注释时，先尝试重构，试着让所有注释都变得多余。**
- **正当用途**：记述"为什么这么做"、标记没有十足把握的区域、记录将来的打算。
- **本仓库**：与 AGENTS.md 约定一致——注释只陈述代码自身无法表达的约束（如 `RngState` 为何原地 mutation），不叙述下一行做什么。
